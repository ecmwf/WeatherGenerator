# Infrastructure

How WeatherGenerator is built, run, and developed. Summary: everything compute runs on
SLURM-managed HPC clusters (development focus: GH200 nodes, aarch64); running the model
locally is not explicitly supported yet. The software stack has two layers: a per-cluster
base environment (uenv or modules) and, on top of it, uv managing the project environment.

## Repositories and forks

- Upstream is `github.com/ecmwf/WeatherGenerator`; development usually happens on
  personal forks, with PRs back to upstream. Remotes in a clone typically include the
  upstream plus one or more forks — never identify a code state by commit alone, always
  as (repository, commit).
- `WeatherGenerator-private` is a sibling repository (expected at
  `../WeatherGenerator-private`, overridable via `WEATHERGEN_PRIVATE_REPO_PATH`) holding
  private HPC configs used by e.g. `scripts/actions.sh create-links`, and the SLURM
  launch tooling (`hpc/launch-slurm.py`, per-cluster scripts). It may contain
  credentials — never read files that look like secrets. Split rule: anything that
  defines a model or affects training results goes in the public repo; machine- or
  team-specific paths and settings go in the private one — never hardcode HPC paths in
  the public repo. Its own docs: `../WeatherGenerator-private/README.md`,
  `../WeatherGenerator-private/doc/getting-started.md`; agent-oriented docs
  (`AGENT-README.md`, `hpc/DOCS-HPC.md`) exist only on some branches of the private
  repo — the checkout must be on the right branch to see them.
- `weathergen-research` is a further sibling only some users have (experiment
  planning, documentation, literature); it carries its own instruction files.

## Execution model

- All real runs (training, evaluation, inference, profiling) happen on HPC clusters,
  submitted through the scheduler.
- Running the code locally is not explicitly supported at the moment (planned for the
  near future). Local machines are used for editing, tooling, and CPU-only unit tests
  (`uv sync --extra cpu` on macOS via `scripts/actions.sh sync`).
- Development happens on the HPC (interactive sessions) or locally against the
  constraints above.

## Software stack

Two layers, per cluster:

1. Cluster base environment — provides CUDA, compilers, MPI, etc. Two paradigms exist
   across our HPCs: `uenv` and environment `modules`; which one (and the exact
   loads) varies per cluster. Module loading is done in each user's `~/.bashrc` on the
   cluster. Details are not yet documented (see TODO).
2. Project environment — uv, on top of the base environment. This layer is identical
   across clusters and machines:
   - Python 3.12, pinned in `.python-version`.
   - `pyproject.toml` — declared dependencies; the source of truth.
   - `uv.lock` — locked exact versions; regenerated by uv, never edit by hand.

```bash
uv sync                 # create/update the env from pyproject.toml + uv.lock
uv run <command>        # run a command inside the env
uv add <package>        # add a dependency (updates pyproject.toml and uv.lock)
```

Never `pip install` into the env — it bypasses the lock and drifts contributors apart.

`scripts/actions.sh sync` picks the right extra per platform (GPU on Linux, CPU on
macOS); `scripts/actions.sh sync-safe` is a slower sync that survives LUSTRE cache
corruption on HPC filesystems.

Supported platforms (`[tool.uv]` environments in pyproject.toml): linux/aarch64,
linux/x86_64, darwin/arm64 (CPU extra only). GPU wheels (e.g. flash-attn) are pinned
per architecture in `[tool.uv.sources]`.

## Hardware

- All clusters use SLURM to manage node access.
- Architectures are mixed across HPCs: aarch64 and x86_64. Development focuses on
  GH200 superchips (Grace CPU + Hopper GPU) — these are aarch64; do not assume
  x86_64 wheels or binaries there.
- GPUs per node varies across HPCs; the main HPCs have 4 GH200 per node, i.e.
  4 GPUs per node.

### JUPITER (JSC)

- Compute (Booster): 5884 nodes, 4× GH200 superchips each (aarch64). Per superchip:
  Grace CPU (72-core Arm Neoverse-V2) with 120 GB LPDDR5X at 512 GB/s; Hopper GPU with
  96 GB HBM3 at 4 TB/s; CPU↔GPU NVLink-C2C at 900 GB/s. GPU↔GPU NVLink at 300 GB/s
  per pair. Network: 4× InfiniBand NDR200 per node (Dragonfly+, adaptive routing).
- Login nodes: 1× GH200 (like compute, but 480 GB CPU memory) — a GPU is present, but
  run compute through SLURM, not on the login node.
- A separate x86 partition (AMD Turin, "Cluster") is being installed; WeatherGenerator
  targets the GH200 Booster.
- Software: RHEL 9; base environment uses the modules paradigm (EasyBuild — GCC, NVHPC,
  CUDA-aware OpenMPI/ParaStationMPI); IBM Storage Scale (GPFS) parallel filesystem.

### Santis (CSCS Alps)

- ~430 compute nodes, 4× GH200 superchips each (aarch64), 4 NICs per node. Santis is a
  partition of the Alps system; its node count changes as nodes are reassigned between
  Alps clusters — don't hardcode it.
- Login nodes: `santis-ln00[1-4]`, assigned on ssh; for editing, compiling, and
  submitting jobs.
- Storage: CWP filesystems and storage policies.
- Base environment: uenv paradigm

## Entry points and run IDs

Entry points are defined in `pyproject.toml [project.scripts]` and run through
`uv run`. CLI flags are dash-separated (`--run-id`, not `--run_id`); full argument
list in `src/weathergen/utils/cli.py`, merge semantics in
`agent_docs/config-system.md`.

```bash
uv run train --config config/<variant>.yml --run-id <run_id>
uv run train_continue --from-run-id <run_id> --mini-epoch <N>  # resume; also chained HPC jobs
uv run inference --from-run-id <run_id>    # inference dates from test_config / --options
uv run evaluate --config <evaluate_cfg>.yml
uv run export ...                          # export inference output
uv run plot_train -fd "{<run_id>: [<job_id>, <label>]}"        # or -fy runs.yml
```

Shared flags: `--options key.subkey=value ...` (highest-precedence overrides),
`--private-config <path>`, `--base-config <path>` (defaults to
`config/default_config.yml`), `--reuse-run-id` (continue/inference keep the source
run's id).

Every training/inference/validation run has an 8-character run ID (lowercase
letter followed by 7 lowercase alphanumerics, `common/config.py:get_run_id`); random
unless set via `--run-id`. Outputs land in the run-id subdirectories listed below.
Continue a run with `train_continue --from-run-id <run_id>`.

Actual HPC launches (SLURM submission, job chaining, MLFlow registration) go through
`../WeatherGenerator-private/hpc/launch-slurm.py`, not by calling `uv run train` on a
login node.

## Integration tests

`integration_tests/` are end-to-end GPU tests (small training runs); they need a GPU
and pre-synced data and run on CSCS CI (`ci/cscs.yaml`), not GitHub Actions. Targets:
`scripts/actions.sh integration-test-single` (smallest, single-stream),
`integration-test-export`, `integration-test-all`; `integration-test` (multi-stream)
and `integration-test-jepa` are outdated.

## Runtime output directories (repo root)

All gitignored. On clusters, `scripts/actions.sh create-links` creates them as symlinks
into the shared working directory (`path_shared_working_dir` from the private repo's
HPC config) — they may point at shared storage, so never assume they are local or
disposable, and never commit their contents.

- `models/<run_id>/` — checkpoints (`common/config.py:get_path_model`, written by
  `trainer.py:save_model`).
- `results/<run_id>/` — per-run results: metrics and train logs (`get_path_run`,
  `utils/train_logger.py`), validation/inference zarr output (`get_path_results`,
  `utils/validation_io.py:write_output`).
- `logs/<run_id>/` — process logs (`common/logger.py:init_loggers`, relative to cwd).
- `plots/` — output of plotting tools (`utils/plot_training.py`, evaluate package's
  default plot dir).
- `output/` — legacy; only referenced in commented-out code, kept in `create-links`
  and `.gitignore`.
- `profiling/` — profiling artifacts from an unmerged branch; not produced by the code
  on this branch.
