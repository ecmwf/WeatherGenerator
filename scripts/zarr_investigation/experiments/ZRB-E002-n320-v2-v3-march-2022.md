# ZRB-E002 — N320, March 2022: Zarr 2 vs Zarr 3 sharded

- Date: 2026-11-03
- Status: done (compute runs: job 2686598)
- Question: for the reader as training uses it, how do the same data compare as a Zarr 2
  store and as the sharded Zarr 3 store, both on GPFS? Read time per window, node
  throughput, cold vs re-read, 1 vs 4 tasks per node; plus size and inode count.

  (private config only), weathergen-configs

- A third variant, the Zarr 2 store packed into a squashfs image, was tested on the login

## Datasets

Both hold March 2022 of the N320 ERA5 dataset, and both live on `/e/scratch`, so the
filesystem is the same.

| Variant | Path | Built by |
| --- | --- | --- |
| `v2` | `$WORK/stage/n320-v2-2022-03.zarr` | `stage_v2_time_slice.py` from the Zarr 2 source in `/e/data1/slmet/ml_training/` |
| `v3` | ZRB-E001's sharded store in `/e/scratch/hclimrep/kreshpa1/zarr3_datasets/` | its owner |

- `v2` is a sparse copy of the source: all metadata (full `dates`, attributes, statistics
  arrays; the source has no `.zmetadata`) and only the `data` chunk files of steps
  378336–379127 (March 2022 plus a day each side; 378360 is 2022-03-01T00, see ZRB-E001).
  The chunk files are copied unchanged, so `v2` returns the source's bytes; the copy checks
  the first and last step. Same training dates as for the source.
- `v3` still has the wrong time metadata (ZRB-E001), so it runs with the ZRB-E001a
  workaround: the same 744 steps given as January 1979. Window index `k` covers the same
  data in both, and `--checksum` checks it. If the store has been fixed by then, use the
  2022 dates for `v3` too (`$D22 $E22` instead of `$D79 $E79` in blocks 4 and 5).

## Design

The copy and a short check run (10 windows per variant: date workaround, checksums) run on a
login node; their times are only indicative (shared node). Timings come from one allocation
of 2 nodes: `A` runs 1-task, `B` runs 4-task, so neither benchmark node has read the files
before (per-node GPFS cache). The storage servers' cache can still be warm from the copy and
earlier runs; nothing in user space can clear it.

A window is 6 h long and reads 6 hourly steps, i.e. 6 chunks (the check run decodes
~6 × 234 MiB per window); windows start every hour, so each step falls into 6 windows. The
reader requests a window as one slice (`ds[start:end]`), so Zarr reads its 6 chunks
concurrently (`async.concurrency`, default 10).

- `s6` = `--stride 6`: every step once (~122 windows of 6 steps). Pass `p1` is the first read
  of the data on that node, `p2` re-reads it straight away.
- `s1` = all windows, shuffled (~740): the training pattern; each step is read 6 times, so
  cache hits are part of the result.

| Node | Tasks | Runs per variant |
| --- | --- | --- |
| A | 1 | `s6-p1`, `s6-p2` |
| B | 4 | `s6-p1`, `s1` |

Chunks are a full time step each (113 variables × 542080 points, ~234 MiB decoded,
~119 MiB on disk), so reads are large and few. `v3` puts 24 of them into one shard file;
its result depends on the shard layout, which the summary prints.

Not covered: DataLoader workers inside a task, other shard sizes, appending to a dataset.

move it until the job has finished. To repeat a run, delete its outputs first (the benchmark

## Result

### Blocks 2–3: data and copy (2026-11-03, login node `jpbl-s01-01`)

- Source `data`: shape `[403248, 113, 1, 542080]`, chunks `[1, 113, 1, 542080]` (one time
  step per chunk), `<f4`, blosc lz4 clevel 5, byte shuffle. 792 chunks = 91.8 GiB, ~119 MiB
  per chunk on disk, ~234 MiB decoded.
- Copy (`--workers 8`): 178 metadata files and 792 chunk files, 91.8 GiB in 21 s
  (4505 MiB/s); first and last step (2022-02-28T00, 2022-04-01T23) identical to the source.
  A first attempt had already read the same source on this node, so the source was probably
  partly cached.

| Variant | Size (MiB) | Inodes |
| --- | --- | --- |
| `v2` | 94017 | 1023 |
| `v3` | 88332 | 342 |

`v3` holds 744 steps (March only), `v2` 792 (a day of margin each side):
94017 × 744 / 792 = 88318 MiB, so the encodings are the same size per step.

### Block 4: check run (2026-11-03, login node `jpbl-s01-01`)

10 windows of the `s6` order per variant (1 warmup, 9 timed), 1 task. Shared login node:
indicative only. `v2` was written on this node in block 3 (GPFS cache possibly warm), `v3`
was not.

| Run | Median ms | p90 ms | Decoded MiB/s | Empty | Checksums |
| --- | --- | --- | --- | --- | --- |
| `check-v2` | 2458 | 2501 | 580 | 0 | 10/10 |
| `check-v3` | 3124 | 3239 | 457 | 0 | 10/10 |

- Both return identical data; the `v3` 1979-date workaround works.
- `v3`: shards of 24 steps (one day) `[24, 113, 1, 542080]`, inner chunks as `v2`, same
  blosc lz4 clevel 5 + shuffle, `crc32c` shard index at the end.

### Zarr concurrency (2026-11-04, login node, from the squashfs diagnosis)

`v2`, 10 windows of the `s6` order, 1 task: median 2486 ms with Zarr's default
`async.concurrency` 10 (seed 4), 3867 ms with `ZARR_ASYNC__CONCURRENCY=1` (seed 5). Reading a
window's 6 chunks concurrently makes `v2` ~1.55× faster; worth varying together with the
shard size for `v3`.

- Same data: every window of every run matches `v2-1t-s6-p1` (or, for windows only `s1`
  reads, `v2-4t-s1`).
- `v3` (24-step shards) is 1.20–1.25× slower per window than `v2` in every configuration,
  as on the login node (1.27×, 1.24×): ~490–620 ms more per window, ~80–100 ms per chunk.
  The compute nodes are no faster than the login node for either variant.
- 1 → 4 tasks per node: node throughput ×4.0 (`v2`) and ×4.0 (`v3`), time per window
  unchanged. 4 tasks don't saturate the node: `v2` at 4 tasks reads ~1.15 GiB/s from disk
  (2325 MiB/s decoded, ~0.51 on-disk/decoded).
- Re-reading (`p2`) and the training pattern (`s1`, each step read 6 times) change the time
  per window by at most 3% (`v3-1t-s6-p2` is even 2% slower than `p1`). Per-window time is
  not set by GPFS reads at this scale but by something a warm cache doesn't remove (decode,
  copies in the reader, per-request latency); a `--nsys` run would show where.
- Empty windows: 5 in both `s1` runs, none in `s6`. Both variants agree on them (checksums),
  so they come from the window set, not the encoding; likely windows at the end of the date
  range, which `s6` skips. Not checked.

## Conclusion

For training-style reads of N320 ERA5 on JUPITER, the sharded Zarr 3 store with 24-step
shards costs ~1.2× the read time per window of the Zarr 2 store with one file per step, on
login and compute nodes, cold and warm, at 1 and 4 tasks per node. Its gain is files: 342
vs 1023 inodes for this month (~400k chunk files for the full 1979–2024 dataset in Zarr 2
vs ~17k shards of 24 steps), at the same bytes per step.

Next: ZRB-E003, shard size (and Zarr's `async.concurrency`, see above) for `v3`; and a
profile of where `v3`'s extra ~80–100 ms per chunk goes.
