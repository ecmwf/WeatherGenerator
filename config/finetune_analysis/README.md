# Fine-tuning sdnbfpve towards the operational analysis

Branch `shmh40/dev-ssl-diffusion/finetune-analysis`, from the live commit df6c675f. The live
checkout (`sdnbfpve-realtime/`) is a separate worktree and is not affected.

## Code changes (src/weathergen/datasets/data_reader_anemoi.py)

* `fill_missing_channels: true` (per stream, opt-in): channels the checkpoint expects
  but the store lacks are read as all-NaN columns, so the target keeps the head's
  81 channels (the loss masks NaN). Needed for q_10, absent from the analysis store.
  Without the flag a missing channel raises, as before.
* `statistics:` on a store with extra variables: anemoi requires every variable of
  the data in the statistics dataset, so only the shared variables are read. Needed for
  ERA5_in: the v4 analysis store has cl, fscov, sro, ssro, urban, which the training
  store lacks. No effect when the variable sets agree (live).

Both are checked against the real stores (ERA5 target: 81 channels, q_10 NaN, the other 80
equal to the store; ERA5_in: training-store stats, data equal to the training store
before 2024-05).

## Configs

* `streams/` is generated by wg-nrt `finetune/make_wg_streams.py` from
  `finetune/streams_finetune_analysis.yaml`. That list is checked by
  `finetune/check_streams.py --start 2024-07-01`, so don't edit `streams/` by hand.
* `stage1_decoder.yml`: decoder only, 2 forecast steps, from sdnbfpve.
* `stage2_latent.yml`: encoder + forecast engine, 8 steps, decoder frozen, from stage 1.

Target choices: the operational analysis with its own statistics. `strd`/`ssrd` have weight 0
(6-h accumulations here, 1-h in ERA5), so the fine-tuned model's strd/ssrd are not
meaningful. When a fine-tuned model goes live, its ERA5 stream must read this analysis
store too, for the same statistics and orography.

## Running (on ag)

From wg-nrt, on an ag login node (scripts in wg-nrt `finetune/ag/`; own venv
`$WG_AG_DIR/venv_sdnbfpve_finetune`, so the live forecast's venv is untouched):

    finetune/ag/build_env.sh                    # once, and when uv.lock changes
    finetune/ag/submit.sh smoke                 # stage 1, 16 samples, 1 GPU (gpu_debug, or add -p gpu -q ng -t 01:00:00)
    finetune/ag/submit.sh stage1 -p gpu -q ng --gpus-per-node=N --ntasks-per-node=N -t <time>
    finetune/ag/submit.sh stage2 <stage-1 run id> [mini-epoch] <same sbatch options>

The smoke run must show finite losses and a sane validation before training. Watch
activity and spectra per lead against sdnbfpve for blurring.

Things the scripts and configs handle, inherited from sdnbfpve's checkpoint config:
- `general.istep: 0` in both stages: the checkpoint's step count would otherwise put the
  LR schedule past warmup, skip mini-epochs, and load an optimizer state for a different
  set of trainable weights;
- `parallel_scaling_policy: constant`: the checkpoint's `const` is rejected by this code;
- `world_size_original` = this run's GPU count (sets AdamW's betas for the batch);
- `samples_per_mini_epoch` is split across the GPUs;
- a run's last checkpoint is `<run>_chkpt0000<num_mini_epochs>` (there is no `_latest`);
  stage 2 starts from stage 1's best mini-epoch by validation (`<run>_chkpt0000<k>` is
  the model after mini-epoch k), the last (8) if none is given;
- stage 1 is short and validated after each of its 8 small mini-epochs: the decoder's
  gain comes early, and a long run (gdv8da6d) gave most of it back.
Each mini-epoch writes a ~5 GB checkpoint (model + optimizer) to the shared models dir.

The block patterns (`freeze_modules`) are matched against names without DDP's `module.`
prefix (fixed in `model/utils.py`, 2026-10-17). Before that, multi-GPU runs never put the
frozen blocks in eval mode, so they trained with their dropout and latent noise on
(gdv8da6d); 1-GPU runs were not affected.

Stage 1 trains the decoder in eval mode (`eval_modules`, applied in `Trainer.train()`,
2026-10-17): its dropout (0.1, hardcoded) changes its output by ~0.03 sigma in every
channel between train and eval mode, so a decoder fitted with dropout on scores far
better on the training path than in validation or inference (z_500 3 m against 8.5 m
for the same weights and windows) and gives its eval gain back as training goes on
(s9xm73r0, gdv8da6d). Training losses from runs before this are not comparable with
validation. Stage 2 does the same for the layers of the encoder and forecast engine,
but keeps the forecast engine's latent noise on (it is applied by the forecast engine
module itself, which stays in train mode). Each mini-epoch logs the top-level blocks
that still have layers in train mode ("Blocks in train mode: ...").
